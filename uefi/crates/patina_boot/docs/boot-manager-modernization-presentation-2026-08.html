Boot Manager Modernization

Modernize BDS as a
reusable architecture.

Move from a platform-specific boot-manager implementation to a tested Patina framework with explicit OEM policy, compatibility gates, and measurable outcomes.

This deck is the program view. It combines the architecture, current evidence, known gaps, and delivery roadmap without making SRE or capsule behavior the selling point.

Why modernize

The boot manager is still a platform integration boundary.

BDS

Required architecture

Patina reaches DXE, but every production platform still needs BDS sequencing, image launch, and failure policy.

C

Policy and mechanism are coupled

The reference path combines generic UEFI behavior, platform hooks, compatibility behavior, and manual resource ownership.

N

Adopters repeat integration

Without a shared framework, each Patina consumer retains C BDS or creates another one-off boot manager.

Modernization is not a language port. It is a clearer ownership boundary for boot mechanism, platform policy, and evidence.

The problem statement is organizational and architectural. A Patina ecosystem without a reusable BDS framework leaves a major part of firmware integration outside the shared architecture.

Target architecture

Mechanism upstream. Policy remains with the platform.

BootDispatcher Installs the BDS architectural protocol and enters the boot framework
->
BootOrchestrator Defines the platform-owned ordering and boot-source decisions
->
Helpers + strategies Provide reusable parsing, connection, events, device paths, and image launch
Patina owns a stable framework. OEMs retain recovery, UI, device choice, provisioning, and product policy.

This is the core design decision. The reusable contribution is not a Surface boot flow; it is the dispatcher, orchestrator contract, generic helpers, test seams, and compatibility expectations.

Evidence today

The framework is running, measured, and testable.

4.306 s patina_boot mean across three verified warm boots
4.320 s C BDS mean on the same device and Patina DXE core
78+ host tests covering parsing, events, cleanup, connection, and fallback
The observed whole-firmware difference was -13.7 ms (-0.3%), smaller than run-to-run variation.

Both datasets were verified under equivalent normal-boot conditions. This supports whole-firmware parity. It does not isolate C versus Rust implementation cost because the two boot managers still execute different policy details.

Architecture advantage

Move important failure modes into enforceable boundaries.

Type

Lifecycle

Result<!, EfiError> makes a successful BDS return unrepresentable.

Bounds

Firmware input

Load-option offsets, UTF-16 descriptions, and every device-path node length are checked before conversion.

Own

Resources

Owned device paths and explicit cleanup reduce dependence on long-lived pointers and allocation pairing.

Rust does not eliminate policy bugs. It makes more invalid states impossible and makes remaining behavior reproducible in host tests.

Avoid claiming that Rust is automatically safer. The supported claim is that this design provides narrower unsafe boundaries, explicit ownership, checked parsing, and deterministic tests for firmware behavior that is otherwise difficult to exercise.

Claim boundary

What the evidence proves—and what it does not.

Proven
  • Patina can boot the device through the Rust framework.
  • No material whole-firmware regression was observed.
  • Core parsing and orchestration mechanisms are host-testable.
  • Policy can be separated from reusable BDS mechanism.
Open
  • Intrinsic C-versus-Rust implementation cost.
  • Complete UEFI BDS semantic compatibility.
  • End-to-end security superiority over the C path.
  • Portability beyond the current hardware consumer.

This slide is important for credibility. The modernization case is already strong enough to continue, but final upstream and OEM decisions need the compatibility, security, portability, and matched-policy evidence on the roadmap.

Semantic parity

The matrix turns compatibility into explicit decisions.

Implemented and tested
  • BootOrder ordering and active-option filtering
  • Bounded EFI load-option and device-path parsing
  • EndOfDxe and ReadyToBoot mechanisms
  • Boot-policy LoadImage and five-minute watchdog
  • Progress markers and returned-image fallback
Compatibility decisions
  • Fail-closed EndOfDxe + ReadyToLock transition
  • BootNext, BootCurrent, and OptionalData
  • OS indications and non-Boot option categories
  • Complete partition identity and ambiguity rejection
  • OEM-controlled fallback-source policy
Issue #196 is the contract: supported, platform policy, partial, planned, or intentionally not targeted.

The matrix prevents two bad outcomes: silently missing behavior that OEMs assume exists, or copying every EDK2 policy into the shared crate without deciding whether it belongs there.

Security workstream

Prove security properties with adversarial evidence.

#191

Lock transition

Make EndOfDxe and DxeSmmReadyToLock an indivisible, fail-closed prerequisite for image loading.

#192

Boot-source identity

Match complete partition identity, reject ambiguity, and require explicit fallback policy.

#193/#194

Adversarial validation

Differentially fuzz firmware inputs and execute a Secure Boot and fault-injection matrix.

The security claim should be: specific invariants are enforced and tested—not that the implementation is secure because it is Rust.

The strongest proposed architecture is a locked-boot capability that can only be created after successful security transition and is required by image-loading APIs.

Performance workstream

Move from parity evidence to implementation attribution.

Matched policy Define the same minimal behavior for C and Rust arms
->
Shared markers Measure connection, events, LoadImage, StartImage, and ExitBootServices
->
Randomized A/B Run 10+ interleaved repetitions and report distributions, p50, and p95
The decision metric is a bounded implementation cost with phase attribution—not a single favorable mean.

Issue #195 owns this evidence. The existing 4.306 versus 4.320 second result remains useful, but only as whole-firmware parity under different policy implementations.

Delivery roadmap

The board sequences architecture before claims.

Iteration 11 Harden the design

Iteration 12 plan Generate evidence

Iteration 13 plan Validate adoption

GitHub currently exposes Iterations 10 and 11. Iterations 12 and 13 are represented by planned dates until the rolling project creates those iteration records.

Decision gates

One program supports two bounded decisions.

Patina

Upstream the framework

Accept the dispatcher, orchestrator contract, generic helpers, compatibility matrix, tests, and maintenance model.

OEM

Pilot the implementation

Adopt after platform parity, security validation, matched-policy performance, and a second reference consumer meet agreed gates.

Approve the modernization roadmap now; make upstream and product decisions against explicit evidence gates.

The immediate ask is not unconditional production replacement. It is agreement on the architecture and evidence plan, followed by separate upstream and OEM decisions when the relevant gates close.
