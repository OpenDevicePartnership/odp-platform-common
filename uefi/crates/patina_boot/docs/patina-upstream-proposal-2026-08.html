Patina upstream proposal

Make boot policy a
first-class component.

patina_boot gives Patina a reusable BDS architecture instead of leaving every platform to rebuild boot orchestration.

This is an upstream architecture proposal, not a request to merge Surface policy. The reusable contribution is BootDispatcher, BootOrchestrator, helpers, strategies, and tests.

The gap

Patina reaches DXE. Platforms still need a boot manager.

BDS

Required architecture

A Patina firmware still needs the BDS architectural protocol and UEFI boot sequencing.

N

Platform reinvention

Without a shared component, each adopter builds or retains a separate C boot manager.

API

Missing policy boundary

Patina needs a stable place for platform boot decisions without coupling them to DXE core.

Patina's value is weakened if every platform must leave the architecture for C BdsDxe or invent an incompatible Rust BDS stack.

The contribution

Mechanism upstream. Policy downstream.

BootDispatcher Installs BDS and enters orchestration
->
BootOrchestrator Small platform-owned policy contract
->
Helpers + strategies Reusable UEFI sequencing and device discovery
Upstream does not own OEM policy. It owns a tested framework that makes OEM policy composable.

This separation is the central maintainability argument. Surface-specific recovery remains in patina_sre; generic boot primitives belong in Patina.

Evidence

It combines real-firmware proof with testable invariants.

-0.3%

Whole-boot parity

4.306 s versus 4.320 s mean on the same MAA and Patina DXE core.

78+

Host tests

Malformed variables, cleanup, events, device paths, and sequencing execute without hardware.

Type

Lifecycle invariant

Result<!, EfiError> prevents BDS from reporting success by returning.

The value is architectural reuse with measured performance parity—not a claim that Rust wins a stopwatch contest.

Both arms were verified under normal-boot conditions on the same device and Patina DXE core, making the total firmware measurements comparable. The result does not isolate the boot-manager implementation because the C and Rust managers still differ in connection, console, BootNext, event, and failure policy.

Bug prevention

The design targets recurring firmware failure modes.

Bounds

Corrupt variable data

EFI load-option offsets and every device-path node length are checked before unsafe conversion.

Own

Lifetime mistakes

Owned device paths and buffers replace long-lived borrowed pointers and manual allocation pairing.

CI

Cleanup and ordering

Watchdog disable, event behavior, fallback, and connect/dispatch convergence have deterministic tests.

Rust does not remove policy bugs. It makes more invalid states impossible and more remaining states reproducible.

The C BDS + UefiBootManagerLib surface inspected for comparison is about 9.8K lines with 176 allocation/free call sites and 71 assertions. The Rust framework is not yet feature-equivalent, so do not present this as a size win. Present it as evidence for explicit ownership and smaller review boundaries.

Upstream quality bar

Merge the framework with explicit acceptance gates.

2

Reference consumers

Keep the MAA integration and add a QEMU or second-platform orchestrator; SRE is one consumer, not the architecture.

UEFI

Compliance matrix

Document BootNext, BootOrder, events, watchdog, failure, and console behavior.

CI

Regression gates

Test feature combinations, unsafe boundaries, code size, and host benchmarks.

These gates make the proposal low-risk for maintainers. They demonstrate genericity, specification coverage, and a sustainable maintenance plan.

Upstream decision

Accept patina_boot as Patina's boot-policy framework.

Core

Merge upstream

Dispatcher, orchestrator trait, generic helpers, strategies, documentation, and tests.

OEM

Keep policy external

Platform-specific recovery, UI, device choices, and business logic remain downstream.

Own

Define maintainers

Name reviewers, compatibility expectations, and the path for new generic helpers.

Upstream the reusable mechanism; let platforms prove the policy.

The ask is intentionally bounded. Patina gains a complete architectural story through BDS, while maintainers avoid taking ownership of Surface-specific behavior.
