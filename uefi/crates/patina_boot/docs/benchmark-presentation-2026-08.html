patina_boot microbenchmark results

What the cycle data says, what it does not, and what we need before performance gating.

August 11, 2026 Issue #183 Source: PR #160 / commit 7a7b5e3

Open with the distinction between engineering characterization and a product performance claim.

Executive readout

Predictable scaling; unstable baseline

141 Kcyc connect_all at 512 handles, three-run median
240 Kcyc expand_device_path at 512 handles, three-run median
>0.998 Linear-fit R-squared for both helpers
6 / 8 Cases with more than 10% same-host observed range
The algorithms scale cleanly with topology size, but the current cycle harness is not stable enough for a 10% CI regression gate.

The headline is not "fast" or "slow." The headline is that scaling is understood, while repeatability is the next engineering constraint.

Method

Hardware-free, synthetic, worst-case where it matters

connect_all

  • Topologies: 1, 16, 128, and 512 synthetic handles.
  • First pass connects every handle once.
  • Second pass confirms that no new handles were created.
  • Includes handle enumeration and BTreeSet tracking.

expand_device_path

  • Topologies: 1, 16, 128, and 512 synthetic device paths.
  • Every handle publishes a valid GPT device path.
  • The matching partition is deliberately last.
  • Measures a full worst-case topology scan and path splice.
Criterion 0.5 Custom rdtsc cycle measurement 3 s warmup + 100 samples + approximately 5 s collection

These are helper costs against mocks. They exclude real driver binding, storage I/O, firmware services, and platform boot policy.

Interpretation

The implementation shape is understandable

1.7x Worst-case 512-handle expansion vs. 512-handle connect
277 Median-fit cycles added per connect_all handle
464 Median-fit cycles added per expand scan handle

What is encouraging

  • No super-linear growth appears through 512 handles.
  • Large-topology per-handle cost is stable in order of magnitude.
  • The harness catches early-return and fixture failures.

What still dominates

  • Fixed overhead distorts tiny topologies.
  • Host scheduling and TSC measurement noise affect repeats.
  • Mocks omit real UEFI driver and protocol costs.

The slope is the most useful engineering result. Absolute single-run values should not be treated as contractual baselines.

Before a 10% CI gate

  • Serialize timestamp reads with fences or rdtscp.
  • Pin CPU affinity and process priority.
  • Run on an isolated, fixed-power host.
  • Commit or otherwise pin the benchmark dependency lock.
  • Store multi-run distributions, not a single point baseline.
The #108 "within 5%" reproducibility criterion is not met yet.

This is not a failure of the algorithms. It is evidence that measurement hardening must precede regression enforcement.

Claim boundary

What we can and cannot say today

Supported

  • The merged harness runs without firmware hardware.
  • Both helper costs grow approximately linearly with topology size.
  • Large-topology primitive costs are in the low hundreds of thousands of reference cycles.
  • We now have a concrete path to automated performance visibility.

Not supported yet

  • "Patina is X% faster than C BdsDxe."
  • A total BootOrchestrator::execute() cycle number.
  • A platform boot-time improvement claim.
  • A reliable 10% per-PR regression gate.

Use this slide to prevent the microbenchmarks from being quoted as end-to-end boot performance.

Roadmap

From helper data to a credible headline

1

Harden cycles

Serialize TSC reads, pin the host, and demonstrate less than 5% repeatability.

2

Measure execute

Unblock #124 with a StandardBootServices test factory.

3

Add QEMU / FPDT

Land #118 and #119 for end-to-end BDS timing.

4

Gate and compare

Enable #120/#122/#123, then add the C baseline and OEM-facing claim.

Recommendation: treat the current numbers as engineering characterization, then fund measurement hardening and the execute() factory as the next two deliverables.
