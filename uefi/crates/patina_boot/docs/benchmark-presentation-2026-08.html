Boot Manager Modernization

Why patina_boot + patina_sre

A memory-safe, customizable boot architecture with integrated recovery and measured performance on real hardware.

August 14, 2026 Issue #183 MAA FPDT: August 14, 2026 Microbench source: PR #160 / commit 7a7b5e3

Lead with the OEM value: safer boot policy, explicit customization, and recovery integrated into the same architecture. Performance is supporting evidence that adoption does not require accepting an unbounded boot-time cost.

Executive readout

The adoption case is safety, control, and recovery

Rust Memory-safe boot orchestration replaces new boot-policy logic in C
Policy OEMs choose device discovery, hotkeys, consoles, and boot fallbacks
SRE Recovery remains available when Windows or normal boot state is damaged
-0.3% Clean isolated mean delta versus C BDS on MAA
OEM proposition: gain a safer and more adaptable boot architecture with integrated recovery, while keeping measured firmware performance in the same operating range as the existing implementation.

Do not sell the migration as "Rust is faster." Sell the capabilities and engineering model, then show that performance is measurable, bounded, and tunable.

OEM value

One architecture covers normal boot and recovery

patina_boot: explicit boot policy

  • BootDispatcher supplies the UEFI BDS architectural protocol.
  • BootOrchestrator lets each OEM define its boot flow without forking a monolithic BDS implementation.
  • Device discovery, console setup, hotkeys, boot selection, and fallback behavior are independently testable.
  • Policy can be optimized for the platform instead of connecting every possible device by default.

patina_sre: recovery in the boot flow

  • Handles Surface recovery hotkeys before normal OS dispatch.
  • Can boot an SRE payload directly from NVMe BP1 when the normal OS path is unavailable.
  • Integrates capsule, DFCI, and recovery policy with the same sequencing and device-discovery model.
  • Provides a path to serviceability even when boot variables or the Windows installation are damaged.
The differentiator is not another boot feature. It is an OEM-owned policy boundary with recovery designed into it.

This is the core adoption slide. Explain that patina_boot is the customization boundary and patina_sre is a concrete production use of that boundary.

What the result means

  • The corrected patina_boot arm is in the same performance band as C BdsDxe.

Engineering headline: no material patina_boot whole-boot penalty was observed under the measured normal-boot conditions.

The clean Rust samples were 4.2516, 4.4224, and 4.2449 seconds. The valid C samples were 4.3648, 4.2224, and 4.3728 seconds. Treat the -0.3% mean delta as parity because the sample is small and the managers are not yet policy-identical.

Performance claim boundary

The current result proves parity, not exact cost

What was measured

  • FPDT covers the whole firmware interval from ResetEnd through ExitBootServices.
  • Both images use the same Patina DXE core and exclude patina_sre.
  • Both datasets were verified under equivalent normal-boot conditions.
  • The paths do not yet execute an identical phase-by-phase platform policy.
  • The observed total difference is negligible relative to run-to-run spread.

What we must prove next

  • Finalize a common minimal-policy contract for C BdsDxe and BootDispatcher.
  • OEM-policy A/B: equivalent console, capsule, DFCI, hotkey, recovery, and boot-option behavior.
  • Common phase markers that reconcile device connection, policy, image loading, and handoff to total FPDT time.
  • At least 10 randomized and interleaved boots per arm.
We can claim no material whole-boot regression in the clean isolated smoke test. We cannot yet assign an exact implementation-only delta.

The normal-boot checks make the total firmware measurements comparable. Matching connection, console, BootNext, event, and failure policy is still required before assigning the measured difference to C versus Rust implementation cost.

What is encouraging

  • No super-linear growth appears through 512 handles.
  • Large-topology per-handle cost is stable in order of magnitude.
  • The harness catches early-return and fixture failures.

What still dominates

  • Fixed overhead distorts tiny topologies.
  • Host scheduling and TSC measurement noise affect repeats.
  • Mocks omit real UEFI driver and protocol costs.

The slope is the most useful engineering result. Absolute single-run values should not be treated as contractual baselines.

Before a 10% CI gate

  • Serialize timestamp reads with fences or rdtscp.
  • Pin CPU affinity and process priority.
  • Run on an isolated, fixed-power host.
  • Commit or otherwise pin the benchmark dependency lock.
  • Store multi-run distributions, not a single point baseline.
The #108 "within 5%" reproducibility criterion is not met yet.

This is not a failure of the algorithms. It is evidence that measurement hardening must precede regression enforcement.

Claim boundary

What we can and cannot say today

Supported

  • patina_boot provides an explicit, customizable boot-policy boundary.
  • patina_sre demonstrates integrated recovery on real MAA hardware.
  • The clean isolated MAA run shows no material whole-boot regression versus C BdsDxe.
  • The merged harness runs without firmware hardware.
  • Both helper costs grow approximately linearly with topology size.

Not supported yet

  • "Patina is X% faster than C BdsDxe."
  • That the observed -14 ms mean difference proves patina_boot is faster.
  • Phase-by-phase parity between the measured firmware images.
  • A reliable 10% per-PR regression gate.

Separate the adoption case, which is already concrete, from performance attribution, which still needs controlled A/B evidence.

Roadmap

Prove parity, isolate cost, then optimize

1

Clean baseline

Completed: same DXE core, equivalent normal-boot conditions, and no patina_sre.

2

Match minimal policy

Align connection scope, BootNext, console, events, and failure handling between both managers.

3

Instrument and scale

Flash shared loader markers and run at least 10 randomized, interleaved boots per arm.

4

Optimize and gate

Tune device discovery, harden repeatability, and gate regressions after attribution is stable.

Recommendation: adopt based on safety, customization, and recovery value; use the controlled A/B work to establish the final performance envelope.

The clean smoke result removes the suspected performance regression. Remaining work increases confidence and attributes time to phases rather than chasing an unexplained whole-boot penalty.
