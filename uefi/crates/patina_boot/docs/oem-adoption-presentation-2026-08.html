Boot Manager Modernization

Safer boot.
Explicit policy.

Patina + patina_boot encode boot invariants, isolate unsafe firmware boundaries, and make platform policy testable without hardware.

This is the thesis. Recovery is one possible policy built on the architecture, not the primary reason to replace C BDS.

Why change

Boot policy should not be a C monolith.

1

Risk

Boot-critical policy is difficult to change safely.

2

Rigidity

Platform customization becomes patching, not composition.

3

Hidden state

Raw pointers, global state, and manual cleanup make failure paths difficult to prove.

Keep this short. The problem is not that C BDS lacks features. The problem is the engineering model for changing and validating platform boot policy.

The architecture

Mechanism, policy, and firmware boundaries are separate.

BootDispatcher UEFI BDS lifecycle and one-time context
->
BootOrchestrator Small OEM-owned policy contract
->
Typed helpers Device paths, variables, events, image launch

Unsafe UEFI calls stay in narrow helpers; platform policy composes those helpers; the dispatcher owns the BDS lifecycle.

What the OEM gets

Boot bugs move from hardware discovery to review and CI.

Type

Invalid lifecycle blocked

Result<!, EfiError> makes a successful BDS return unrepresentable.

Bounds

Malformed NVRAM rejected

Boot options and device-path node lengths are validated before pointer conversion.

78+

Failure paths tested

Watchdog cleanup, bad variables, events, device paths, and dispatch convergence run on the host.

Concrete examples: BootConfig requires an initial device; optional behavior uses Option rather than sentinel pointers; load-option parsing checks every offset and node length; tests verify watchdog cleanup when StartImage fails.

Architecture evidence

Specific bug classes have explicit defenses.

Own

Lifetime and cleanup bugs

Owned buffers and device paths reduce leaks, use-after-free, and stale-pointer reuse.

Bound

Runaway enumeration

Controller discovery tracks attempted handles, detects convergence, and has iteration limits.

Mock

Sequencing regressions

Connect/dispatch ordering and failure propagation are deterministic unit tests.

The inspected C BDS + UefiBootManagerLib surface spans about 9.8K lines with 176 allocation/free call sites and 71 assertions. This is not a feature-equivalent size comparison; it shows why narrow ownership and test boundaries matter.

Do not claim Rust eliminates logic bugs. Claim that memory lifetime, buffer bounds, invalid states, and cleanup obligations are either encoded or concentrated into reviewable boundaries. The remaining logic is easier to exercise in CI.

No performance claim until every parity row passes.

The two release images already share the Patina DXE core, platform firmware, device, and no-patina_sre boundary. They are not yet policy-equivalent: stock C BdsDxe performs BootNext, console, hotkey, recovery, variable, and platform-hook work that the isolated Rust manager currently skips. Close or explicitly exclude those gaps before presenting timing as implementation cost.

Clean benchmark

Measured normal-boot totals overlap.

4.320 s C BDS mean, three warm boots
4.306 s patina_boot mean, three clean warm boots
Observed difference: -14 ms / -0.3%, inside run-to-run variation.

Both arms were verified under normal-boot conditions on the same device and Patina DXE core. The whole-firmware totals can be compared, but the 14 ms difference cannot be assigned solely to C versus Rust because the managers still execute different policy details.

The C samples were 4.3648, 4.2224, and 4.3728 seconds, averaging 4.3200 seconds. The patina_boot samples were 4.2516, 4.4224, and 4.2449 seconds, averaging 4.3063 seconds. Both datasets were verified as normal boots under the same platform state. The 13.7 ms mean difference is smaller than either arm's run-to-run spread. It is a whole-firmware observation; assigning it to the boot-manager implementation requires identical connection, console, BootNext, event, and failure policy.

These are wall-clock phase durations, not CPU instruction counts. In the valid C arm, ResetEnd to OS Loader LoadImage averages 3,066.8 ms; LoadImage to StartImage averages 29.4 ms; StartImage to ExitBootServices Entry averages 992.9 ms; ExitBootServices averages 230.9 ms. The corrected Rust total is comparable, but its current firmware does not populate the two OS-loader FPDT fields. An instrumented Rust EFI now reports the same progress codes around LoadImage and StartImage for the next phase-level run.

OEM decision

Adopt Patina for the policy model, not a speed claim.

What is proven Normal-boot performance is at parity; lifecycle, bounds, cleanup, and sequencing have explicit defenses.
What OEMs gain Composable policy, hardware-free tests, smaller unsafe boundaries, and optional recovery implementations.
Pilot Patina + patina_boot; evaluate recovery policy separately.

The OEM case is the architecture and assurance model. Gate adoption on required boot outcomes, malformed-variable tests, fault injection, firmware resource budgets, and a larger randomized performance run. patina_sre can remain a reference consumer rather than the headline.
